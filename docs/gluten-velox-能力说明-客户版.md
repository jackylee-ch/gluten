# Gluten + Velox 向量化引擎能力说明（基于 Gluten 1.5.0）

> 面向对象：评估或已采用本产品的业务与技术决策者
> 版本基线：Gluten 1.5.0，Velox 分支 `gluten-1.5.0`，参考 Spark 3.5.5
> 说明：本文给出的所有数字均来自对该版本源码的逐项核对，不含估算

## 1. 一句话结论

在标准离线数仓与交互式分析的批处理 SQL 场景中，Gluten 1.5.0 已覆盖 Spark 全部核心算子与约
八成常用函数；未覆盖的部分绝大多数落在流式计算、Python/UDF、Dataset 强类型 API 三类
**架构性场外**能力上。产品能力边界清晰、可预测，并且任何不支持的情形都会**自动回退**到原生
Spark 执行，不影响作业正确性与可用性。

## 2. 核心设计前提：不支持等于回退，不等于报错

这是理解后续所有数字的前提。

Gluten 以 Spark 插件形态工作，在物理计划阶段逐节点判断能否卸载到向量化引擎。判断不通过的
节点保留原生 Spark 实现，与已卸载节点在同一作业内混合执行。因此：

- **不存在"因为不支持某个函数而作业失败"的情形**，只有该节点不获得加速
- 客户无需为迁移改写 SQL，可直接在既有作业上开启
- 加速比取决于计划中被卸载节点的占比，而非全有或全无

这一机制决定了产品的风险特征：**上限是性能收益，下限是持平原生 Spark**。

## 3. 算子支持情况

### 3.1 总体分布

Spark 3.5 共有 156 个物理算子类。其中 37 个是抽象基类与 AQE 调度包装、35 个是 DDL 与元数据
命令，这两类不涉及数据面计算，不构成加速对象。剩余 **84 个真实数据处理算子**的分布如下：

| 类别 | 数量 | 占数据面算子 |
|---|---:|---:|
| 卸载到 Velox 原生向量化执行 | 27 | 32% |
| 列式执行（保持列式管道，避免行列转换开销） | 8 | 10% |
| **合计获得加速** | **35** | **42%** |
| 回退原生 Spark | 49 | 58% |

单看 42% 这个比例并不能反映实际收益，原因见下节：被覆盖的 35 个算子承载了批处理 SQL 的
绝对主体计算量，而未覆盖的 49 个中有七成属于非批处理场景。

### 3.2 已覆盖的算子（批处理 SQL 主干完整）

原生向量化执行（27 个），按功能归类：

| 能力 | 覆盖算子 |
|---|---|
| 数据扫描 | 文件扫描、V2 批扫描、Hive 表扫描 |
| 过滤与投影 | Filter、Project |
| 聚合 | 哈希聚合、排序聚合、对象哈希聚合 |
| 关联 | Shuffle 哈希连接、广播哈希连接、排序合并连接、笛卡尔积、广播嵌套循环连接 |
| 排序与限制 | Sort、Limit、TopN（排序+限制融合） |
| 分析函数 | Window、Window 分组限制 |
| 集合与展开 | Union、Expand（GROUPING SETS/CUBE/ROLLUP）、Generate（explode 等） |
| 数据交换 | Shuffle Exchange（含原生 Shuffle 写） |
| 数据写入 | 文件写入、Iceberg 追加写与覆盖写 |
| 采样与 Python | Sample、标量 Python UDF |

**这一集合覆盖了 TPC-H / TPC-DS 全部查询模式**：扫描下推、过滤、多表连接、多阶段聚合、
窗口分析、排序分页、集合运算、GROUPING SETS。典型离线数仓作业与 BI 交互查询的计划节点，
主体都在此列。

列式执行（8 个）虽不进入 Velox 计算，但保持列式数据格式流转，避免了行列转换的高昂开销：
广播交换、子查询广播、Coalesce、CollectLimit/CollectTail、Range、Arrow Python UDF、
内存表缓存。

### 3.3 未覆盖的算子：七成属于架构性场外

49 个回退算子的构成：

| 类别 | 数量 | 说明 |
|---|---:|---|
| Structured Streaming | 16 | 流式状态算子、水位线、流式去重与连接。**产品定位为批处理加速，流式不在范围内** |
| Python / pandas / R UDF | 12 | pandas UDF、分组 map、R 相关。仅标量 Python UDF 在支持范围内 |
| Dataset 强类型 API | 8 | `map` / `flatMap` / `mapGroups` 等。**这些算子执行的是用户 JVM 闭包，原理上无法向量化** |
| V2 行级写入 | 5 | MERGE INTO 行级计划、动态分区覆盖、Delta 行级写。Iceberg 追加写与覆盖写已支持 |
| 其他零散 | 8 | 脚本转换（`TRANSFORM ... USING`）、RDD 扫描、会话窗口聚合等 |

**前三类合计 36 个，占未覆盖算子的 73%，均属于产品定位之外或技术上不可向量化的能力。**
真正落在批处理 SQL 场景内、仍待补齐的只有 13 个，且集中在行级写入与少数边缘算子上。

## 4. 函数支持情况

### 4.1 总体分布

Spark 3.5 共暴露 435 个内置函数（标量 357、聚合 62、窗口 9、生成器 7）：

| 类别 | 总数 | 完全支持 | 部分支持 | 不支持 |
|---|---:|---:|---:|---:|
| 标量函数 | 357 | 240 | 26 | 91 |
| 聚合函数 | 62 | 54 | 1 | 7 |
| 窗口函数 | 9 | **9** | 0 | 0 |
| 生成器函数 | 7 | **7** | 0 | 0 |
| **合计** | **435** | **310** | **27** | **98** |

- **可向量化执行（完全 + 部分）：337 个，占 77.5%**
- **窗口函数与生成器函数 100% 覆盖**
- 聚合函数覆盖 89%（55/62），是数仓场景最关键的一类

"部分支持"指函数本身已向量化，但在特定参数或配置下回退。例如 `from_json` 在指定 options
时回退、正则类函数在使用环视（lookahead/lookbehind）语法时回退——因为向量化实现基于 RE2
引擎，不支持该语法。

### 4.2 未覆盖函数的实际影响远小于 98 这个数字

98 个未覆盖函数按类别分布如下，其中相当一部分对实际作业没有性能影响：

| 类别 | 数量 | 实际影响评估 |
|---|---:|---|
| 日期时间 | 23 | 其中 6 个是常量类（`current_date`、`now` 等，Spark 优化阶段已折叠为字面量，不参与运行时计算）；2 个是已支持函数的别名；3 个是流式窗口；4 个涉及 TimestampNTZ / interval 构造。**真正影响批处理的仅 8 个**，主要是时区转换与部分时间戳解析 |
| 杂项 | 20 | 其中 10 个是元数据/环境函数（`current_user`、`input_file_name` 等，语义上不是计算）；4 个是加解密与 JVM 反射调用（`aes_encrypt`、`reflect`，原理上无法向量化）；其余为 HLL sketch 与 bitmap 函数 |
| 字符串 | 18 | 主要是格式化类（`format_string`、`format_number`）、编解码类（`encode`、`decode`）与部分正则扩展函数 |
| 数学 | 11 | 三角函数（`sin`/`tan`/`tanh`）、自然对数 `ln`、`bround`、整除 `div` 等 |
| XML 路径 | 9 | `xpath` 系列，使用面较窄 |
| CSV / Map / 其他 | 7 | `from_csv`/`to_csv`、`map_from_arrays` 等 |

去除常量折叠、别名、流式、元数据、原理上不可向量化这几类之后，**真正需要关注的功能缺口约
50 个**，集中在字符串格式化、部分三角函数、XML 路径三个方向。

### 4.3 需要提示的一点

函数支持清单由自动化脚本从测试日志生成，其判定逻辑是"未观测到回退即视为支持"。因此少量
未被测试覆盖的函数会被乐观标记。我们已核实并明确的例外有 4 个：`split_part`、
`approx_percentile`、`percentile_approx`、`percentile`——清单标记为支持，实际会回退。

对客户的实际影响仅限于性能预期，不影响结果正确性。若您的核心作业重度依赖某个特定函数，
建议在 POC 阶段实测确认，我们也可协助逐一核验。

## 5. 数据类型支持情况

类型准入是一条全局规则，对所有已卸载算子统一生效。

**完整支持**：BOOLEAN、TINYINT、SMALLINT、INT、BIGINT、FLOAT、DOUBLE、STRING、BINARY、
DATE、TIMESTAMP、DECIMAL（精度 1–38 全范围）、NULL。

**复杂类型完整支持且可任意嵌套**：ARRAY、MAP、STRUCT。`ARRAY<STRUCT<...>>`、
`MAP<STRING, ARRAY<STRING>>` 这类嵌套结构在扫描、过滤、投影、聚合、连接、Shuffle 全链路
均可向量化。

**不支持**（涉及这些类型的算子回退）：

| 类型 | 影响场景 |
|---|---|
| `TimestampNTZType` | 无时区时间戳，Spark 3.4+ 新类型 |
| 用户自定义类型（UDT） | 主要影响 Spark MLlib 的 Vector / Matrix 类型 |
| `DayTimeInterval` / `CalendarInterval` | 时间间隔类型 |

## 6. 需要客户重点关注的四个边界

我们主动披露以下四点，以便您准确预估收益：

**一、ANSI 模式**
开启 `spark.sql.ansi.enabled` 后，整个执行计划全量回退，不获得任何加速。若业务依赖 ANSI
语义，需在 POC 阶段确认。

**二、写入路径是覆盖最窄的环节**
原生向量化写入仅支持 Parquet（含 Hive SerDe 的 Parquet）。此外，字段携带自定义元数据、
设置 `maxRecordsPerFile`、使用分桶表等情形均会回退写入。**读取加速不受此影响** —— 读写可
独立评估。

**三、ORC 弱于 Parquet**
ORC 扫描不支持 TIMESTAMP 列、部分深层嵌套结构与 `char(n)` 类型。若您的数据湖以 ORC 为主，
扫描环节的收益会低于 Parquet 场景。**建议以 Parquet 作为向量化加速的首选存储格式。**

**四、大小写敏感模式**
产品仅支持 Spark 默认的大小写不敏感模式。

## 7. 版本适配范围

| Spark 版本 | 支持状态 |
|---|---|
| 3.2 / 3.3 / 3.4 | 支持 |
| **3.5** | **支持，且为主要验证版本（推荐）** |
| 4.0 | 预览，不建议生产使用 |

推荐组合：**Spark 3.5 + Parquet + 关闭 ANSI 模式 + 默认大小写不敏感**，此组合下算子与函数
覆盖度最高、验证最充分。

## 8. 结论与建议

**能力总结**

| 维度 | 覆盖情况 |
|---|---|
| 数据面算子 | 84 个中 35 个加速；未覆盖的 73% 属流式/UDF/闭包等场外能力 |
| 批处理 SQL 主干 | 扫描、过滤、投影、聚合、连接、排序、窗口、集合运算 **全覆盖** |
| 内置函数 | 435 个中 337 个可向量化（77.5%） |
| 窗口 / 生成器函数 | **100% 覆盖** |
| 聚合函数 | 89% 覆盖 |
| 复杂类型 | ARRAY / MAP / STRUCT 全链路支持，可任意嵌套 |
| 失败风险 | **无**，不支持即自动回退，结果与原生 Spark 一致 |

**适用场景**：以 Parquet 为主的离线数仓 ETL、交互式 BI 查询、TPC-H / TPC-DS 类分析型负载。
这类负载的计划节点主体落在已覆盖算子集合内，加速效果最为充分。

**需要谨慎评估的场景**：Structured Streaming 作业、重度依赖 pandas UDF 或 Dataset 强类型
API 的作业、以 ORC 为主要存储格式的数仓、依赖 ANSI 语义的业务。

**建议的推进方式**：选取 3–5 个代表性生产作业做 POC。由于回退机制的存在，POC 无需改写任何
SQL，可直接开启对比。我们可提供逐作业的算子卸载率分析，量化说明每个作业的实际加速覆盖面，
再据此决定推广范围。
