# Gluten + Velox 向量化引擎能力说明

> **面向对象**：技术 VP 及业务决策者
> **产品版本**：Gluten 1.5.0（Velox 分支 `gluten-1.5.0`）
> **目标 Spark 版本**：**Spark 3.3.2**
> **数据来源**：对 Gluten 1.5.0 源码与 Spark 3.3.2 发行包的逐项核对，不含估算

## 1. 结论摘要

在以 Parquet 为主的离线数仓与交互式分析场景中，Gluten 1.5.0 已完整覆盖 Spark 3.3.2 批处理
SQL 的全部核心算子，以及约八成常用内置函数。未覆盖部分绝大多数落在流式计算、Python/R UDF、
Dataset 强类型 API 三类**产品定位之外或技术上无法向量化**的能力上。

产品边界清晰可预测，且任何不支持的情形都会**自动回退**至原生 Spark 执行，不影响作业成功率
与结果正确性。

| 关键指标（Spark 3.3.2） | 数值 |
|---|---|
| 数据处理算子获得加速 | 76 个中 **33 个**（43%） |
| 未覆盖算子中属产品定位之外 | **72%** |
| 批处理 SQL 主干算子 | **全覆盖** |
| 内置函数可向量化 | 386 个中 **316 个（81.9%）** |
| 窗口函数、生成器函数 | **100% 覆盖** |
| 聚合函数 | **96% 覆盖** |
| 作业失败风险 | **无**，不支持即自动回退 |

## 2. 核心机制：不支持等于不加速，不等于报错

这是理解后续所有比例的前提。

Gluten 以 Spark 插件形态运行，在物理执行计划阶段**逐节点**判断能否卸载到向量化引擎。判断
不通过的节点保留原生 Spark 实现，与已卸载节点在同一作业内混合执行。

由此产生三个对决策至关重要的性质：

- **不存在"因不支持某函数导致作业失败"的情形**，只是该节点不获得加速
- **无需为迁移改写任何 SQL**，可在既有作业上直接开启对比
- 加速比取决于执行计划中被卸载节点的占比，而非全有或全无

产品的风险特征因此非常明确：**上限是显著性能收益，下限是持平原生 Spark**。

## 3. 算子支持情况

### 3.1 总体分布

Spark 3.3.2 共有 142 个物理算子类。其中 32 个是抽象基类与 AQE 调度包装、34 个是 DDL 与元数据
命令，这两类不涉及数据面计算，不构成加速对象。剩余 **76 个真实数据处理算子**分布如下：

| 类别 | 数量 | 占数据面算子 |
|---|---:|---:|
| 卸载至 Velox 原生向量化执行 | 25 | 33% |
| 列式执行（保持列式管道，规避行列转换开销） | 8 | 10% |
| **合计获得加速** | **33** | **43%** |
| 回退原生 Spark | 43 | 57% |

单看 43% 无法反映实际收益。原因是：被覆盖的 33 个算子承载了批处理 SQL 的绝对主体计算量，
而未覆盖的 43 个中有 72% 属于非批处理场景（详见 3.3）。

### 3.2 已覆盖算子：批处理 SQL 主干完整

原生向量化执行（25 个），按能力归类：

| 能力域 | 覆盖算子 |
|---|---|
| 数据扫描 | 文件扫描、V2 批扫描、Hive 表扫描 |
| 过滤与投影 | Filter、Project |
| 聚合 | 哈希聚合、排序聚合、对象哈希聚合 |
| 表关联 | Shuffle 哈希连接、广播哈希连接、排序合并连接、笛卡尔积、广播嵌套循环连接 |
| 排序与分页 | Sort、Limit、TopN（排序+限制融合优化） |
| 分析函数 | Window |
| 集合与展开 | Union、Expand（GROUPING SETS / CUBE / ROLLUP）、Generate（explode 等） |
| 数据交换 | Shuffle Exchange（含原生 Shuffle 写） |
| 数据写入 | Iceberg 追加写、Iceberg 覆盖写 |
| 采样与 Python | Sample、标量 Python UDF |

**该集合覆盖 TPC-H / TPC-DS 全部查询模式**：扫描下推、过滤、多表关联、多阶段聚合、窗口
分析、排序分页、集合运算、多维聚合。典型离线数仓 ETL 与 BI 交互查询的执行计划节点，主体
均在此列。

列式执行（8 个）虽不进入 Velox 计算，但维持列式数据格式流转，规避了行列转换的高昂开销：
广播交换、子查询广播、Coalesce、CollectLimit / CollectTail、Range、Arrow Python UDF、
内存表缓存。

### 3.3 未覆盖算子：72% 属产品定位之外

43 个回退算子的构成：

| 类别 | 数量 | 说明 |
|---|---:|---|
| Structured Streaming | 13 | 流式状态算子、水位线、流式去重与流式连接。**产品定位为批处理加速，流式不在范围内** |
| Python / pandas / R UDF | 10 | pandas UDF、分组 map、R 相关算子。标量 Python UDF 已在支持范围内 |
| Dataset 强类型 API | 8 | `map` / `flatMap` / `mapGroups` 等。**这些算子执行用户 JVM 闭包，原理上无法向量化** |
| V2 数据源写入 | 3 | 动态分区覆盖、通用 V2 写。Iceberg 追加写与覆盖写已支持 |
| 其他零散 | 9 | 脚本转换（`TRANSFORM ... USING`）、RDD 扫描、会话窗口聚合、指标收集等 |

**前三类合计 31 个，占未覆盖算子的 72%**，均属产品定位之外或技术上不可向量化。真正落在
批处理 SQL 场景内、仍待补齐的仅 12 个，集中在 V2 写入与少量边缘算子。

## 4. 函数支持情况

### 4.1 总体分布

Spark 3.3.2 共暴露 386 个内置函数：

| 类别 | 总数 | 完全支持 | 部分支持 | 不支持 |
|---|---:|---:|---:|---:|
| 标量函数 | 320 | 226 | 26 | 68 |
| 聚合函数 | 50 | 47 | 1 | 2 |
| 窗口函数 | 9 | **9** | 0 | 0 |
| 生成器函数 | 7 | **7** | 0 | 0 |
| **合计** | **386** | **289** | **27** | **70** |

- **可向量化执行（完全 + 部分）：316 个，占 81.9%**
- **窗口函数与生成器函数 100% 覆盖**
- **聚合函数覆盖 96%**（48/50），是数仓场景最关键的一类，仅 `count_min_sketch` 与
  `histogram_numeric` 两个低频函数未覆盖

"部分支持"指函数本身已向量化，但特定参数或配置下回退。例如 `from_json` 在指定 options 时
回退；正则类函数在使用环视（lookahead / lookbehind）语法时回退——因向量化实现基于 RE2
引擎，该引擎不支持此语法。

### 4.2 未覆盖函数的实际影响远小于数字本身

70 个未覆盖函数按类别分布，其中相当一部分对实际作业性能无影响：

| 类别 | 数量 | 影响评估 |
|---|---:|---|
| 日期时间 | 13 | 其中 4 个为常量类（`current_date`、`current_timestamp`、`current_timezone`、`now`，Spark 优化阶段已折叠为字面量，不参与运行时计算）；1 个是已支持函数 `extract` 的别名；2 个为流式窗口；2 个为 interval 构造。**真正影响批处理的仅 4 个**：`months_between`、`timestamp_seconds`、`to_date`、`to_timestamp` |
| 字符串 | 13 | 格式化类（`format_string`、`format_number`）、编解码类（`encode`、`decode`）、数值转换类（`to_number`） |
| 杂项 | 12 | 其中 8 个为元数据 / 环境函数（`current_user`、`input_file_name`、`typeof` 等，语义上非计算）；4 个为加解密与 JVM 反射调用（`aes_encrypt`、`reflect`，**原理上无法向量化**） |
| 数学 | 11 | 三角函数（`sin` / `tan` / `tanh`）、自然对数 `ln`、`bround`、整除 `div`、`try_*` 算术 |
| XML 路径 | 9 | `xpath` 系列，使用面较窄 |
| CSV / Map / 聚合等其他 | 12 | `from_csv` / `to_csv`、`map_from_arrays`、`sequence`、`parse_url`，以及 2 个低频聚合函数 |

剔除常量折叠、函数别名、流式专用、元数据访问、原理上不可向量化这几类（合计 21 个）之后，
**真正需要关注的功能缺口约 49 个**，集中在字符串格式化、部分三角函数、XML 路径三个方向。

### 4.3 需向客户说明的一点

函数支持清单由自动化脚本从回归测试日志生成，判定逻辑为"未观测到回退即视为支持"。因此少量
未被测试覆盖的函数会被乐观标记。我们已核实并明确的例外有 4 个：`split_part`、
`approx_percentile`、`percentile_approx`、`percentile`——清单标为支持，实际执行时会回退。

此类偏差**仅影响性能预期，不影响结果正确性**。若核心作业重度依赖某特定函数，建议在 POC
阶段实测确认，我方可协助逐一核验。

## 5. 数据类型支持情况

类型准入为一条全局规则，对所有已卸载算子统一生效。

**完整支持**：BOOLEAN、TINYINT、SMALLINT、INT、BIGINT、FLOAT、DOUBLE、STRING、BINARY、
DATE、TIMESTAMP、DECIMAL（精度 1–38 全范围）、NULL。

**复杂类型完整支持且可任意嵌套**：ARRAY、MAP、STRUCT。`ARRAY<STRUCT<...>>`、
`MAP<STRING, ARRAY<STRING>>` 等嵌套结构在扫描、过滤、投影、聚合、关联、Shuffle 全链路均可
向量化。

**不支持**（涉及这些类型的算子回退）：

| 类型 | 影响范围 |
|---|---|
| 用户自定义类型（UDT） | 主要影响 Spark MLlib 的 Vector / Matrix 类型 |
| `DayTimeInterval` / `CalendarInterval` | 时间间隔类型 |

> Spark 3.3.2 尚无 `TimestampNTZType`（无时区时间戳）的常规使用路径，该限制在 3.3 场景下
> 不构成实际影响。

## 6. 需重点评估的四项边界

我方主动披露以下四点，便于准确预估收益：

**一、ANSI 模式**
开启 `spark.sql.ansi.enabled` 后整个执行计划全量回退，不获得任何加速。若业务依赖 ANSI
语义，需在 POC 阶段确认。

**二、数据写入是覆盖最窄的环节（3.3 场景需特别注意）**
Spark 3.3 的写入路径与 3.4+ 不同：原生向量化写入通过 `NativeWritePostRule` 实现，且
**默认关闭**（需显式设置 `spark.gluten.sql.native.writer.enabled=true`）。启用后仅支持
Parquet（含 Hive SerDe 的 Parquet），且复杂类型（ARRAY / MAP / STRUCT）会导致写入回退。

**读取加速不受此影响** —— 读、写可独立评估，多数客户的收益主体来自读取与计算环节。

**三、ORC 弱于 Parquet**
ORC 扫描不支持 TIMESTAMP 列、部分深层嵌套结构与 `char(n)` 类型。若数据湖以 ORC 为主，扫描
环节收益将低于 Parquet 场景。**建议以 Parquet 作为向量化加速的首选存储格式。**

**四、Spark 3.3 需要类覆盖，部署时须确认加载顺序**
Spark 3.2 / 3.3 上，Gluten 需要覆盖 27 个 Spark 内部类（主要涉及 `FileFormatWriter`、
`ParquetFileFormat`、`OrcFileFormat` 等写入与扫描相关类），因为这些能力在该版本尚未开放
公共 API。**部署时必须确保 Gluten jar 的类加载优先级高于原生 Spark jar。**

若使用了经过定制的 Spark 发行版，需先确认上述类是否被改动过，否则定制内容将被覆盖。使用
非官方支持的 3.3 补丁版本可能在运行时触发 `NoSuchMethodError`。

> 说明：Spark 3.4 及以上版本不存在此约束（改用 Spark 开放的 `WriteFilesExec` 机制）。
> 如后续有升级计划，此项运维负担可随之消除。

## 7. 版本适配范围

| Spark 版本 | 支持状态 | 说明 |
|---|---|---|
| 3.2 | 支持 | 需类覆盖 |
| **3.3** | **支持（当前目标版本）** | 需类覆盖；官方验证基线为 3.3.1 |
| 3.4 | 支持 | 无需类覆盖，写入机制更完善 |
| 3.5 | 支持，验证最充分 | 无需类覆盖；算子与函数覆盖度最高 |
| 4.0 | 预览 | 不建议生产使用 |

**关于 3.3.2 的兼容性**：Gluten 1.5.0 的 `spark-3.3` 配置以 **3.3.1** 为验证基线。运行在
3.3.2 上时，Gluten 会正常加载 3.3 适配层并输出一条版本不完全匹配的告警日志，不影响功能。
3.3.1 与 3.3.2 之间为补丁级差异，未涉及 Gluten 依赖的内部接口变更。**建议在 POC 阶段以
3.3.2 实际环境完成一轮回归验证。**

**升级到 3.5 的增量收益**（供规划参考）：Spark 3.5 新增 49 个内置函数，其中 21 个已被 Gluten
支持；算子层面新增 `WindowGroupLimitExec`（rank 类窗口过滤下推优化）已支持；写入路径改为
`WriteFilesExec` 机制，无需类覆盖，且原生写默认开启。

## 8. 结论与推进建议

### 能力总结（Spark 3.3.2）

| 维度 | 覆盖情况 |
|---|---|
| 数据面算子 | 76 个中 33 个加速；未覆盖的 72% 属流式 / UDF / 闭包等场外能力 |
| 批处理 SQL 主干 | 扫描、过滤、投影、聚合、关联、排序、窗口、集合运算 **全覆盖** |
| 内置函数 | 386 个中 316 个可向量化（**81.9%**） |
| 窗口 / 生成器函数 | **100% 覆盖** |
| 聚合函数 | **96% 覆盖** |
| 复杂类型 | ARRAY / MAP / STRUCT 全链路支持，可任意嵌套 |
| 作业失败风险 | **无**，不支持即自动回退，结果与原生 Spark 一致 |

### 适用场景

以 Parquet 为主的离线数仓 ETL、交互式 BI 查询、TPC-H / TPC-DS 类分析型负载。此类负载的执行
计划节点主体落在已覆盖算子集合内，加速效果最为充分。

### 需谨慎评估的场景

Structured Streaming 作业、重度依赖 pandas UDF 或 Dataset 强类型 API 的作业、以 ORC 为主要
存储格式的数仓、依赖 ANSI 语义的业务、以写入为主要瓶颈的作业。

### 推进建议

1. **选取 3–5 个代表性生产作业做 POC。** 由于回退机制存在，POC 无需改写任何 SQL，可直接
   开启对比。
2. **优先验证读取与计算环节**，写入加速在 3.3 上需单独开启并单独评估。
3. **由我方提供逐作业的算子卸载率分析**，量化说明每个作业的实际加速覆盖面，再据此决定
   推广范围。
4. **确认部署环境的类加载顺序**，这是 3.3 场景下唯一需要额外关注的运维事项。
